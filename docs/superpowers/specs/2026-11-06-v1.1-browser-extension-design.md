# Fetchdeck v1.1, Spec B: browser extension

Date: 2026-11-06
Status: draft for review
Part of v1.1. Depends on Spec A (settings store and Settings dialog), which is built first.

## Goal

Catch downloads in Chrome and Edge and hand them to Fetchdeck, IDM-style: automatic capture of large downloads, a right-click "Download with Fetchdeck" on links, and support for downloads that need a login (cookies, Referer, User-Agent).

## Scope

In:
- Chromium extension (Manifest V3) for Chrome and Edge, loaded unpacked.
- Automatic capture of browser downloads at or above a size threshold; right-click on links.
- A local server in the app, off by default, protected by a pairing token.
- Cookies, Referer and User-Agent passed to the engine, encrypted on disk, deleted when no longer needed.
- A confirmation dialog in Fetchdeck for every capture.

Out:
- Firefox, a Chrome Web Store listing, extension auto-update.
- Native messaging, a content script, Alt-to-bypass.
- Speed limits, scheduling, checksums.

## Decisions

| Question | Decision |
|---|---|
| How downloads are caught | Auto-capture plus right-click. |
| Browsers | Chrome and Edge, Manifest V3. |
| Connection to the app | Local server on 127.0.0.1 with a pairing token (not native messaging, not a custom protocol). |
| Logged-in downloads | Send Cookie, Referer and User-Agent to the engine. |
| Where credentials live | Encrypted on disk with Electron safeStorage, deleted when done, cancelled or removed. Memory only if encryption is unavailable. |
| Capture UX | Fetchdeck's Add dialog for every capture; Cancel means "download in the browser". |
| What is captured | http(s) downloads with a known size of at least 5 MB (adjustable); toolbar switch turns capture off. |
| Capture mechanism | `chrome.downloads.onCreated`: pause the browser download, send to Fetchdeck, cancel and erase it on accept, resume it otherwise. |
| Alt-to-bypass | Dropped (needs a content script on every page). Replaced by the toolbar switch and the dialog's "Download in browser". |

## 1. Cookies and headers through the engine and queue

The engine makes three kinds of request, none with custom headers today: `probe` (and the re-probe when a link expires), `runSegment`, and the single-stream fallback fetch in `download.ts`.

- **Allowed headers.** Only `Cookie`, `Referer` and `User-Agent`. Anything else is dropped. The engine's own headers (`Range`, `Accept-Encoding`, `If-Range`) always win.
- **Engine option, not record field.** `Download` gets a `headers` provider option (`() => Promise<RequestHeaders>`). `probe`, `runSegment` and the single-stream fetch take a `headers` argument. Credentials are never added to `DownloadRecord`.
- **Cookies stay with their site.** `Cookie` is sent only to the origin of the original URL. If the probe redirects to another origin (a CDN), requests to that origin carry Referer and User-Agent but no Cookie. The plan must confirm with two fake servers on different ports, and check that Node's `fetch` does not forward `Cookie` across a cross-origin redirect.
- **`AuthStore` (queue).** Injected interface with `save(id, headers)`, `load(id)`, `delete(id)`. `add(url, saveDir, options?)` accepts optional `headers`; when present they go to the store and the `Download` is built with a provider that loads from it. Credentials are deleted when a download finishes, is cancelled, or is removed. An errored download keeps them so Retry works. `load()` deletes credential files with no matching record.
- **App implementation.** A safeStorage-backed `AuthStore` writing `<id>.auth` in the user-data folder (Windows: DPAPI). If `safeStorage.isEncryptionAvailable()` is false, it keeps credentials in memory only; resume after a restart then fails with "Needs the link from your browser again". Nothing is ever written unencrypted.

## 2. Local server (`app/main/extensionServer.ts`)

- Node `http` server bound to `127.0.0.1` only, fixed port 47600. If the port is busy the server stays off and Settings says "Port 47600 is in use". Off by default; a Settings switch turns it on.
- API (JSON, `/v1`):
  - `GET /v1/ping` returns `{ app: "fetchdeck", version }`.
  - `POST /v1/captures` takes `{ url, cookie?, referer?, userAgent?, filename?, size? }` and returns `202 { captureId }`.
  - `GET /v1/captures/:id?wait=20` waits up to 20 seconds and returns `{ state: "pending" | "accepted" | "dismissed" }`.
- **Capture flow.**
  1. The extension pauses the browser download and posts the capture.
  2. The app puts it in a capture line (cap of 20 pending). The Add dialog shows one at a time.
  3. Confirm: main calls `queue.add` with the cookies and the extension cancels and erases the browser download. Dismiss, no answer, or app closed: the extension resumes the browser download.
- **Expiry.** If the extension stops polling for 60 seconds, the capture is dropped and its dialog closes with a short note, so a capture the browser has already resumed cannot be confirmed.
- **The page never sees cookies.** The renderer gets only `{ captureId, url, filename, size }`. The link preview runs in main by `captureId`. The renderer calls `captures.accept(id)` or `captures.dismiss(id)`.
- **Checks on every request, in order:**
  1. `Host` must be `127.0.0.1:47600` or `localhost:47600` (blocks DNS rebinding).
  2. `Authorization: Bearer <token>` compared with `timingSafeEqual`. Token is 32 random bytes, generated on first enable, stored via safeStorage where available. After 10 failures in a minute, 429 for a minute.
  3. If `Origin` is present it must start with `chrome-extension://`. Web pages cannot read the token, and their cross-origin requests with an `Authorization` header need a preflight that the server never approves.
  4. Body at most 64 KB, JSON only. URL through the existing `asUrl`. Only allowed keys, values length-limited, control characters rejected.
  5. Regenerating the token takes effect immediately; the old token stops working.

## 3. Extension package (`extension/`)

- New workspace package `@fetchdeck/extension`: TypeScript, Manifest V3, bundled with esbuild into `extension/dist`. CI typechecks, tests and builds it.
- Permissions: `downloads`, `contextMenus`, `storage`, `cookies`, host permission for `http://127.0.0.1:47600/*`. Reading cookies for any site needs host access to all sites (`<all_urls>`). This is a broad permission, acceptable for a personal unpacked extension, to be revisited before any store listing, and documented in the README.
- Parts (the Chrome API is injected as a typed `ChromeLike`):
  - `shouldCapture`: http(s) only, never `blob:` or `data:`, capture on, size known and at least the threshold (default 5 MB). Unknown sizes stay in the browser.
  - `buildCapture`: cookies from `chrome.cookies.getAll`, Cookie header, Referer and User-Agent.
  - `fetchdeckClient`: `ping`, `postCapture`, `waitForOutcome`; clear errors (not running, wrong token, rejected).
  - Service worker: `downloads.onCreated` then decide, pause, post, wait, cancel and erase on accept, resume otherwise. Right-click "Download with Fetchdeck" on links sends a capture with no browser download involved. Resume within a second if the app is unreachable, and after 3 failed polls mid-wait. Pending captures are kept in `chrome.storage.session` so a service-worker restart mid-wait picks them up again or resumes the browser download.
  - Options page: token field, Test connection (Connected / Wrong token / Fetchdeck not running), threshold, port shown read-only.
  - Popup: on/off switch, status dot, link to Options. Toolbar badge shows "off" when capture is disabled.
- Known limits: POST or form downloads cannot be told apart from GET and might be re-fetched wrongly (the preview shows the real file before you confirm); one-time or signed links can be used up by the browser's first request; Chrome and Edge only.

## 4. App UI

- **Capture dialog.** `AddDownloadDialog` in "from browser" mode: read-only link with a "From browser" tag, preview loaded in main by `captureId`. Buttons: Download (`captures.accept`) and Download in browser (`captures.dismiss`; Esc and closing do the same). Shows "N more waiting". When a capture arrives, main brings the window forward with `revealWindow` and flashes the taskbar button if Windows blocks focus.
- **Settings, "Browser extension" section** (in the Spec A dialog): Enable switch (`extensionEnabled`) that starts or stops the server immediately; status line ("Running on 127.0.0.1:47600", "Off", "Port 47600 is in use"); pairing token masked by default with Show, Copy and Regenerate (Regenerate asks for confirmation); one line of install help (load `extension/dist` in `chrome://extensions`, Developer mode, Load unpacked). The token has its own IPC call and is not part of `settings.get`.
- **New IPC** (typed in `shared/api.ts`, validated in main): `captures.onIncoming`, `captures.preview`, `captures.accept`, `captures.dismiss`, `extension.getStatus`, `extension.setEnabled`, `extension.getToken`, `extension.regenerateToken`.

## 5. Build order, release, risks

Build order: (1) Spec A. (2) Spike, throwaway code, in real Chrome and Edge: can a download be paused from `onCreated`, and do 20-second long-polls keep the service worker alive? If long-polling fails, fall back to short 2-second polls; the API barely changes. (3) Engine headers and queue `AuthStore`. (4) Local server. (5) App UI. (6) Extension, then a manual test pass in Chrome and Edge. (7) Docs, CI and release.

CI and release: add `extension` to workspaces, `typecheck -p extension` to scripts, its tests to `npm run check`; CI builds the extension; the release workflow attaches `Fetchdeck-Extension-<version>.zip` next to the installers and checksums. App and extension share the version (1.1.0).

Docs: README "Browser extension" section (install, pairing, how capture works, the permission note, known limits), and remove it from "Not in v1" and "Known limits". CHANGELOG entry. DECISIONS.md records: local server instead of native messaging, pause then cancel, encrypted cookies deleted when done, Alt-bypass dropped.

Risks: service-worker lifetime during the wait (spike); a tiny download finishing before it can be paused (the 5 MB threshold makes it unlikely; if the item is already complete the extension leaves it alone); one-time and POST downloads; no keyring on some Linux setups (memory only, clear message); port 47600 in use (server stays off, Settings says why).

## Error handling

- App unreachable, wrong token, or server error: the extension resumes the browser download; nothing is lost.
- Invalid capture body: rejected with a plain message and a 4xx status; the extension resumes the browser download.
- Missing or corrupt token or settings: regenerate or fall back to defaults, keep running.
- Credential store unavailable: memory only, with a clear message on resume.

## Testing

- Engine: right headers reach all three request kinds; engine headers cannot be overridden; Cookie dropped on a cross-origin redirect; credentials never appear in record JSON.
- Queue: credentials deleted on done, cancel and remove, kept on error; orphan files cleaned on `load()`; memory-only fallback; existing crash test stays green.
- Server (real `http`, no Electron): each check fails in the right way (wrong Host, missing or wrong token, wrong Origin, oversized body, bad URL, unknown keys, header-injection characters, lockout); captures are shown one at a time; accept and dismiss reach the long-poll; the 20-capture cap; expiry closes the dialog; off when disabled; token regeneration.
- IPC and renderer: captures never expose cookies to the renderer; accept passes cookies to `queue.add`; capture dialog tag, waiting count, accept, dismiss, Esc; settings section switch, hidden token, Regenerate confirmation.
- Extension: `shouldCapture`, `buildCapture`, client against the real server handler, and a state-machine test with a fake `ChromeLike` (accept, dismiss, app down, service-worker restart mid-wait, duplicate events).
- Manual checklist in Chrome and Edge: capture, right-click, toggle, wrong token, app closed, a logged-in download, several captures at once.

`npm run check` stays green on Windows and Linux CI.
